# Core loop and pillars lens

Covers the repeatable engine of the game, how other systems attach to it, the principles that decide what belongs, and the kind of thinking the loop demands.

## When to use

- A document lists many features but no repeating cycle.
- Nobody can say what the player does for most of a session.
- The game is fun once and flat by the tenth repetition.
- Pillars exist but are slogans that never decide anything.
- Features are added or cut by taste rather than by a shared rule.

## Gather

- The claimed core loop, if one is written down.
- A walkthrough of one typical session, or a short timeline of play.
- The feature list and the meta systems: progression, economy, crafting, collection, social.
- Existing pillars or vision statements.
- Target session length and platform.

## Checks

### Find the loop

1. What does the player do repeatedly, at three time scales: seconds (moment to moment), minutes (an encounter or round), session (a run, a day, a match)?
2. For each scale, write the cycle as action, then game response, then state change, then reason to go again. A cycle without a reason to go again is not yet a loop.
3. Can the minute-scale loop be said in one breath, for example "scout, ambush, loot, upgrade, scout"? If not, it is probably several loops tangled together.
4. Is the stated loop really a loop, or a one-way progression (story chapters, a level list) dressed as one?

### Test the loop

1. **Readable**: does the player see what their action changed?
2. **Meaningful**: does the result change what they do next cycle?
3. **Variable**: what makes cycle 50 differ from cycle 1: new combinations, opponents, rules, stakes, knowledge?
4. **Tight**: how long is one cycle, and how much of it is waiting, walking or menu work? Mark dead steps that change nothing.
5. **Self-standing**: if progression and rewards were removed, would the loop still be engaging? If not, the meta is carrying the core.

### Feature-to-loop map

1. For each feature, name the loop step it strengthens. Features that strengthen no step are orphans and candidates for cutting or postponing.
2. Separate the core loop from support loops (progression, economy, social, live events). Support loops should feed the core, not compete with it for time.
3. Check that the economy's sources and sinks both touch the core loop.

### Pillars

1. Infer three to five pillars from the behaviors the game pays off and the experiences it shields, not from aspirations.
2. Each pillar must decide something. Write it as "we choose X even when it costs Y." If a pillar never rejects a feature, it is a slogan.
3. Check pillars against each other for conflicts and against the loop for coverage. A pillar with no supporting system is unbacked.
4. Run two or three current features through the pillars. Do the pillars give a clear keep or cut?

### Cognitive demand

1. Does the loop mainly ask for quick, instinctive play or slow, deliberate planning? Kahneman's fast and slow thinking is a useful frame.
2. Does that mode match the fantasy and the platform? Deep planning on a short mobile commute session, or twitch reaction in a cozy game, is a mismatch.
3. Where the loop switches modes, is there a pause that makes the switch comfortable?

## Common problems

- **Feature pile**: many systems, no single cycle that ties them together.
- **Progression posing as a loop**: the only reason to repeat is the next unlock.
- **Dead steps**: travel, confirmation screens or menu chores between meaningful beats.
- **Sameness**: nothing changes across cycles except numbers.
- **Slogan pillars**: "fun combat", "beautiful world", which never cut anything.
- **Mode mismatch**: the loop asks for a kind of thinking the fantasy or session does not support.

## Fix menu

- Write the loop at three time scales on one page and cut or postpone orphan features.
- Remove or shorten one dead step per cycle.
- Add one source of variation: enemy mix, modifiers, procedural layout, player-made combinations.
- Rewrite each pillar as a trade-off, then test it on a real cut decision.
- Insert a calm planning beat between fast segments, or simplify planning to fit the session.

## Reporting notes

- Show the extracted loop as an arrow chain and mark broken or dead steps.
- Compare the extracted loop with the claimed loop explicitly.
- List orphan features by name.
